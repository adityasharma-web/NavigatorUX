02 — WHY OPTION 1

The Azure-style blade model — icon rail → hierarchy blade → content host → details/actions blade — keeps the drill-down users depend on while letting them open, drill, and close panels to reclaim workspace. It scales to large multi-site trees, matches the enterprise tools the team referenced, and cleanly separates the Navigator shell from the modules it loads. Concepts 2 and 3 are archived for reference but are not the direction.

03 — HOW THE KEY PIECES WORK

Hierarchy & tree

Backend-driven nodes (Blocks → Sites → Modules → Areas → Equipment → Parameters → Charts/Records/Violations). Compact rows, clear expand/collapse, quiet selected state. Loads lazily in production.

Smart filter

Compact filter button → popover with multi-select categories (Module/Area, Site/Block, Object Type, Status). Active pills + count badge; Apply / Clear. Filters the tree only.

Pinned objects

User-profile-scoped, collapsible section at the top of the blade. Open directly without re-drilling; unpin with ×. Supports the "least clicks" goal alongside breadcrumbs.

Content Host

The main area is a labeled hosted region. Selecting a node routes a module/app/chart/report into it. The sample SPC view is clearly marked "sample loaded view" — not owned by the shell.

Details / actions blade

Closable right panel: compact metadata, quiet role/access context, and compact actions (View Data, Open Chart, View Records, Configure Limits). Actions route to their own modules.

Theme & scale

Appearance menu: Light / Dark, Scale 100 / 125 / 150%, Density Compact / Comfortable. Dark mode is the primary visual target; default is 100% compact.

04 — SHELL vs LOADED CONTENT & SECURITY

Navigator shell owns

  • Login / role & security context
  • Icon rail, hierarchy blade, tree filter, pinned
  • Breadcrumbs, routing, theme & scale
  • Details/actions blade, permission-aware visibility

Loaded content (separate)

  • SPC charts, histograms, records tables
  • Dashboards, reports, workflow / process screens
  • Other internal or external application modules

Security is shown subtly after login: a small SUPER-USER badge in the profile and details blade, a locked NCMR module, a disabled admin-only "Archive" action, and facility-scoped access. UI checks are convenience only — the API stays the source of truth, filtering the tree and actions per role and facility.

05 — FOR LATER TECHNICAL PLANNING

React component map (AppShell, IconRail, NavigatorTree, SmartFilter, PinnedList, ContentHost, ObjectDetailsPanel, ActionPanel, Theme/ScaleControls) over an API layer: React → API → authorization → backend/DB → navigator data. The tree, content, and permissions are all server-provided; this mock fixes the UI structure, not the business logic. Components are greenfield / permissive-licensed only — no proprietary UI controls.
